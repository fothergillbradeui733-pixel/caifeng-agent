# 管线接口契约

`qiutian-shijue-zichan-tishici` 与上游 `comic-adapt`、下游 `qiutian-3dman-shipin-tishici` 共享的接口对账单，版本 C2.5。它不是第三事实源；具体定义以本 skill 的 `asset-spec.md` / `output-template.md`、comic-adapt 的 `visual-handoff-card.md` 和下游 skill 的对应规则为准。

修改任何接口时：先改权威落点，再核对对侧，提升本契约版本，最后同时运行资产库机检与下游 `--lib` 机检。

## comic-adapt 上游交接接口

### 固定输入与权威边界

comic-adapt 项目只暴露一个机器入口：

```text
<项目目录>/visual-assets/handoff.md
```

`handoff.md` 必须为 `schema_version: comic-adapt-visual-handoff/1.0` 且 `交接状态：READY`，并通过哈希指向 `source-facts.md`、各集 `episodes/EP-XX.md` 与对应 `scripts/EP-XX.md`。`source-facts.md` 与分集交接是上游事实载体，`handoff.md` 是可重建清单；缓存 JSON 不是事实源。

上游交付的是：剧本实体 ID、类型、规范名与别名、候选 `@资产名`、人物/场景/道具逐集出现、资产化决策、视觉状态维度、生效区间、切换锚、可见事实及证据定位。上游不交付最终文生图提示词，也不替代本技能的旧库复用、正式命名、美术补足、完整卡、音色、状态并行组合与源覆盖审计。

### 导入命令与结果

```text
python <qiutian-shijue-zichan-tishici根目录>/scripts/import_comic_handoff.py \
  <项目目录>/visual-assets/handoff.md \
  [--episodes N或N-M] \
  --output <项目目录>/.comic-adapt-cache/qiutian-shijue-zichan-tishici/handoff-<范围>.json
```

PASS 必须同时满足：schema/READY 正确；顶层和各集未解决项为空；请求集均且仅有一条清单记录；源事实、分集交接和剧本文件存在且 SHA-256 相符；分集引用的实体 ID 在源事实中唯一存在；同一实体没有混用裸基础名与 `_状态词`。输出 JSON 的 `source_facts` 只保留所选集实际引用的实体，`episodes` 保留逐集人物/场景/道具行和对应权威路径。

`COMIC-HANDOFF-IMPORT-PASS` 后，下游以 JSON 作为本轮发现清单，避免重新全量提取已闭合的人物、场景和道具；写卡、消歧时按 JSON 路径和证据锚定点回读。最终仍须运行 `validate_assets.py` 与 `audit_source_coverage.py`，后者负责独立发现上游遗漏。

上游 `原文未明示，交下游美术补足` 只授权审美补足，不授权具名/固定脸角色的身份或剧情事实：脸部审美、识别锚、发型细节、既定服装类别内设计和非功能性场景陈设可由本技能设计并标 `美术补足`；具名角色的性别、年龄、种族，以及文字、品牌、关键功能和剧情线索仍须回源或询问。generic 群像在字段明确授权时可由本技能设定画面性别构成。导入 JSON 是可删除的非权威缓存；生成任务可写项目 `.comic-adapt-cache`，纯只读审计应写会话临时目录。

`COMIC-HANDOFF-IMPORT-FAIL`、入口不存在、请求范围缺集或任一哈希陈旧时，不得读取旧缓存继续生成。删除/忽略本轮缓存，报告精确原因，然后回退 `plot-map.md`、`progress.md` 与按 EP 排列剧本的原始发现流程。旧项目没有初始化交接不阻断传统建库，但回传必须写 `comic-adapt交接：NOT_INITIALIZED`；不得称交接 READY。

### 冲突优先级

事实冲突按“用户本轮明确指令 → 既有有效资产库/同版索引 → 有效 comic-adapt 交接 → 其它项目台账 → 改编剧本 → 原著补充事实”处理。旧库命中时复用其正式卡名和锁定事实；交接中的 `建议@资产名` 只作候选。有效交接与改编剧本不一致通常意味着交接未同步：先按哈希阻断；若哈希一致但语义冲突，定点核证并列为上游事实冲突，不自行把两套事实拼接。

## 缺资产补充文档接口

### 输入

下游冻结本轮缺口后传入：

```text
调用来源：qiutian-3dman-shipin-tishici
当前剧本：{路径}
原分组视频提示词：{路径；允许已含本轮缺失 @资产}
项目目录：{路径}
主资产库：{路径/无}
主资产索引：{路径/无}
既有补充文档：{按 S 序排列的路径列表/无}
缺口清单：{@建议名｜建议类型｜原分组/行号｜剧本证据｜预计复用/近景一致性需求}
既有视觉风格：{风格值/无}
参考风格基调：{主库值/用户指定值/无}
下游管线：qiutian-3dman-shipin-tishici 16:9 3D漫
补充范围：{EP-XX / EP-XX-YY / 批次标识}
输出目录：{路径}
```

先读取主库/索引、全部既有补充、相关剧本证据和原分组正文。`@建议名` 是待审计规范名，不自动构成新资产事实；合法且无冲突时优先保留，减少对原分组的改写。

### 命名与追加规则

- 文件名使用 `{剧本名}_资产库补充_{范围}_S{N}.md`。范围只使用文件名安全字符，例如 `EP-03`、`EP-03-05`、`B001`；`S{N}` 取输出目录中同项目下一空闲正整数，不覆盖旧文件。
- 补充文档是追加层，不是 V1/V{N+1} 全量库，也不配同版索引。后续正式并库是独立任务，届时才输出 V{N+1} 全量库与索引并运行 `--prev`。
- 只新增本轮真正缺失的完整卡、卡内音色和必要的技能特效/状态登记。主库或旧补充已存在的卡不得复制进本补充。
- 明确命中既有资产名或别名时，回传规范既有 `@资产` 并让下游替换建议名；不创建别名占位卡。
- 同名已被不同实体或类型占用时，为新实体选择无冲突规范名并回传精确替换；实体同一性无法确认、别名多指或新旧定义冲突时阻塞该项，不得猜测。
- 既有角色的新状态可以新增 `@角色_状态` 完整卡，但必须从完整既有角色卡逐字继承同脸基础锚点和基础音色。只有索引、无法取得完整锚点时，先取得主库对应卡；取不到则阻塞该状态，不能重造一张脸。
- 同名音色/特效跨文档出现时必须逐字相同；不同文本视为冲突。补充层不得改名、废弃、覆盖或补写既有卡元信息。

### 文档格式

补充文档使用以下壳层；各卡正文逐字遵循 `output-template.md` 对应类型的完整卡格式：

````markdown
# {剧本名}_资产库补充_{范围}_S{N}

## 补充元信息

补充批次：S{N}
补充范围：{范围}
基准资产库：{路径/无}
基准资产索引：{路径/无}
前置补充文档：{按加载顺序列路径/无}
视觉风格：{与主库/索引逐字一致；无主库时写已确定风格}
参考风格基调：{与主库逐字一致；只作用于场景资产；无则写无}
调用来源：qiutian-3dman-shipin-tishici
````

### 代理执行

有空闲代理时，把“读取冻结输入 → 写唯一补充文件 → 运行单文档机检 → 回传路径和闭合映射”作为独立任务交给一个代理；主实例可以继续原分组工作。代理不得修改原分组、主库、索引或旧补充，也不得与其它实例并行写同一输出文件。没有空闲代理时由当前实例串行完成。

### 验证与回传

先校验补充卡自身：

```text
python <qiutian-shijue-zichan-tishici根目录>/scripts/validate_assets.py <补充文档路径>
```

必须修复全部 FAIL。若当前校验器仍按全量库文件名或全剧类别产生补充模式特有 warning，逐项记录；其它可避免 warning 必须修复。补充文档不使用 `--prev`、`--index` 或 `sync_asset_index.py`，也不冒充全量库运行源覆盖审计。

再按事实源顺序对原分组做联合库机检：

```text
python <qiutian-3dman-shipin-tishici根目录>/scripts/validate_3dmh.py <原分组视频提示词> \
  --lib <主资产库或主资产索引> \
  --lib <资产库补充_..._S1.md> \
  [--lib <资产库补充_..._S2.md> ...]
```

主库或主索引始终在前，补充按 S 序加载；无主库时可只传补充文档。联合加载是集合并集，不是覆盖链。每个活动 `@` 必须精确解析到一张卡/一条登记；资产类型、音色、特效或别名有冲突时硬失败。

回传至少包含：

```text
资产库补充文档路径：
补充批次与范围：
联合 --lib 顺序：
缺口闭合映射：{原分组定位｜@建议名｜最终 @/无 @ 最小描述｜处理结果}
需要原位替换：{@旧→@新 / @旧→无 @ 最小描述 / 无}
单文档机检：
联合 --lib 机检：
下游可交付：是/否（否时列未闭合或冲突项）
```

原分组允许先出现缺失 `@`，但最终回传时不能仍是联合库无法解析的悬空引用。正式并库不是补充流程的隐式后置步骤，只有用户明确要求时才执行。

## 多个补充文档合并接口

用于长篇并发任务中各集/批次已生成多个补充文档后的最终收口。合并是生成新的追加层，不是正式全量库升版，也不是对源文档的原位修改。

### 输入与输出

输入必须包含：

```text
调用来源：qiutian-3dman-shipin-tishici 批量收口
主资产库：{路径/无}
主资产索引：{路径/无}
源补充文档：{按 S 序排列的全部路径}
源补充覆盖集：{每个文档对应 EP 范围}
原分组视频提示词：{全部受影响集的路径}
输出目录：{路径}
```

先读取主库/索引和全部源补充文档，建立 `事实键→原文→来源文档→受影响集` 台账。输出文件名使用 `{剧本名}_资产库补充_{总范围}_S{N}.md`，其中 `S{N}` 是输出目录下一空闲正整数。源补充文档保留供审计，不覆盖、不删除、不改名。

合并文档沿用“缺资产补充文档接口”的壳层，并增加：

```markdown
## 合并来源与去重映射

| 事实键/资产 | 保留来源 | 去重来源 | 受影响集 | 结果 |
|:--|:--|:--|:--|:--|

## 冲突清单

| 事实键/资产 | 来源 A | 来源 B | 冲突类型 | 受影响集 | 处理状态 |
|:--|:--|:--|:--|:--|:--|
```

无冲突时 `冲突清单` 保留表头并写 `无`；有冲突时不得产出可交付的合并补充文档，可保留草稿和冲突报告，但必须回传 `下游可恢复：否`。

### 确定性合并规则

按主库/索引→源 S 序建立事实集合：

1. 资产卡以规范 `@资产名` 为键。类型和完整卡正文在统一换行、去除行尾空格后逐字相同，视为同卡同文，只保留最早来源并登记去重映射。
2. 同名卡的类型或任一正文事实不同，视为冲突；不得自动拼接 `出现集`、别名、说明或提示词，也不得选择较新来源覆盖。
3. 音色、技能特效、状态时间线、并行组合登记分别以其左侧规范键为事实键；同键同文去重，同键异文阻塞。
4. 活动卡名与别名在全局只能解析到一个实体和一种类型；别名多指、同名异体、同名异类型全部阻塞。
5. `缺口闭合映射` 按 `原分组定位＋缺口建议名＋最终口径` 去重；同一原分组定位得到不同最终口径时阻塞，并列出受影响集。
6. `可引用 @资产清单`、角色音色表、技能特效表、状态时间线和图片文件名对照表从保留事实重新生成，不从任一源文档整段复制。
7. 不做语义近似合并。两个名称疑似同体但缺少精确别名/实体证据时，登记冲突并阻塞，不能凭相似描述猜测。

### 验证与下游加载

先对合并文档执行：

```text
python <qiutian-shijue-zichan-tishici根目录>/scripts/validate_assets.py <合并补充文档>
```

再逐个对受影响集执行：

```text
python <qiutian-3dman-shipin-tishici根目录>/scripts/validate_3dmh.py <该集原分组> \
  --lib <主资产库或主资产索引> \
  --lib <合并补充文档>
```

最终联合机检不要同时加载合并补充文档和它的源 S 文档。全部受影响集无悬空 `@`、类型/音色/特效/状态冲突后，才把合并文档标为 PASS。

回传至少包含：

```text
合并补充文档路径：
源补充文档→合并文档映射：
保留卡数 / 同卡同文去重数：
冲突清单：{事实键｜冲突类型｜来源｜受影响集}
受影响集：
合并文档机检：
逐集联合 --lib 机检：
最终 --lib 顺序：{主库/索引 → 合并补充文档}
下游可恢复：是/否
```

## 状态时间线接口

生效区间只使用：

```text
EP-A–EP-B
EP-A 起
仅 EP-A
全剧本
EP-A 起 · 场合语义
```

不要用离散集号白名单表达场合穿脱。换装、形态、伤势类必须写 `EP-XX 场次 XX-X＋剧情事件`；恰在集首则写 `EP-XX 集首（承接上集末事件/时跳）`。

角色维度允许：`形态 / 体态 / 服装 / 伤势 / 身份呈现 / 特殊`。`身份呈现` 与其它状态一样必须有切换锚；下游把对应 @状态卡视为角色主状态之一，并在跨集快照中保留该 @引用。

跨维重叠段的唯一口径：主状态卡 + 体态/持物道具卡 + 必要文字锚，不创建维度笛卡尔积组合卡。
