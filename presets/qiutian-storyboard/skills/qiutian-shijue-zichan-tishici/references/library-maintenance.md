## 更新模式

输入含 `{剧本名}_视觉资产库_V{N}.md` 时，旧库为事实源：

- 既有 `@资产名` 和音色行禁止改名、改写或删除。
- 允许新增资产卡、追加「出现集/别名」、补充有证据的新状态。
- 新状态的基础锚点段与既有状态卡逐字相同。
- 输出 V{N+1}，不覆盖旧文件；库头增加「变更记录」。
- 索引同升同出；机检同时带 `--prev` 和 `--index`。
- 输入没有旧库时只能新建 V1，不得自称更新版。

### 角色视觉身份 schema 升级

旧库缺 `设定性别 / 外观呈现 / 呈现性质 / 颜值定位 / 特殊标志`、脸部识别锚点或服装设计方向时，下一版必须全量回填可见角色和 Q版小人：

1. 先从用户指令、剧本、角色台账和原著身份事实取证，不从旧音色、姓名、长发或服装反推视觉性别。
2. 旧卡若使用 `外观呈现：刻意模糊`，在新版本迁移为 `外观呈现：中性`；角色设定确属剧情隐去性别时同时写 `设定性别：剧情刻意未明示`，正文使用“剧情保留性别悬念的中性人物，完整、清晰呈现面孔”，并在说明登记证据。旧库仍可作为 `--prev` 输入，新版本完成迁移后交付。
3. 既有特殊标志、年龄、脸型、骨相和核心记忆点有证据时保持；把当前状态可见的特殊标志逐项写入新字段和文生图正文。旧库无据编造项不得因“旧库锁定”继续漂移，须在变更记录逐项登记纠错依据。
4. 原文未给脸部结构但用户已授权整体美术设计时，可补足颜值定位、审美簇和 1–2 个脸部识别锚点，并在说明标 `美术补足：脸部识别锚点`；删除无识别作用的五官穷举。
5. 旧群像卡若使用“面部弱化辨识度”等弱化人脸表述，在新版本迁移为 3–6 人逐一具有完整、清晰、自然差异化的面孔；原著明确蒙面、遮脸或无脸时保留原著呈现并在说明登记证据。
6. 女扮男装、男扮女装、日常异性化穿着或舞台扮装跨阶段出现时，按 `身份呈现` 拆状态并登记切换锚；仅补字段、静态外观未变化时不强拆。
7. 服装从具体单品堆叠或空泛职业标签升级为 `服装设计方向：`，写清身份场合、外显性格、内在张力和 2–4 个视觉维度；保留原文明示的服装类别和剧情识别点。
8. 变更记录使用 `补充：@角色 视觉身份、特殊标志、脸部锚点与服装方向（依据）`；纠正无据外貌使用 `纠错：@角色 删除/替换无据标志（依据）`。

schema 升级允许为满足新硬字段与群像人脸规则而修改角色或群像提示词，但不得静默改名、改音色或改变有证据的同脸锚点。

### 单状态首拆多状态

既有 `@资产名` 首次增加第二状态时，不保留总卡：

1. 在变更记录登记 `改名：@资产名 → @资产名_状态词（首拆多状态，依据）`。
2. 把旧名写入所有新状态卡「别名」。
3. 把原卡内容迁移为合适的第一个状态卡。
4. 新增其它状态卡；各卡独立完整、锚点段同文。

## 受控改名与废弃

只有以下情况允许改名：

- 回填台账 C 类或用户直接指令，且用户已经明确拍板。
- 单状态首拆多状态；由剧本触发，无需另行拍板，但必须登记。

改名格式：

```text
改名：@旧名 → @新名（依据/拍板日期）
```

新卡使用新名，旧名并入「别名」。发生改名后提醒用户用新库对已产出的全部下游集文件重跑库引用机检。

废弃资产不删卡：

```text
废弃：@资产名（原因）
```

同时在该卡「说明」中注明已废弃及替代口径。

废弃卡必须同时写：

```text
使用状态：已废弃
替代资产：@有效资产名 / 多个 @有效资产名 / 逐镜内联
```

有效卡写 `使用状态：有效`、`替代资产：无`。废弃卡保留在完整库中用于版本追溯，但从可引用清单、状态时间线和图片文件名对照表移除；库尾建立 `资产兼容映射表`，索引同步该表。不得把“历史重复、兼容、旧版、废弃”等维护词继续当作可引用视觉状态。

## 回填台账消费

逐条消费下游回填台账并回写处理结果：

- A 新建：以附卡为底稿，复核命名真值源、多状态必要性、音色四槽、GPT 适配后入库。
- B 补充：追加既有卡的出现集、别名或证据，不改锚点和音色。
- C 改名：走受控改名通道。
- D 不入库：保留不入库结论与理由。
- E 待拍板：整理成用户决策清单，未拍板不改库。

回填条目注明 `已入库/已补充/已改名/不入库/待拍板`，并登记目标库版本。

### 下游逐集事务式直回填

`qiutian-3dman-shipin-tishici` V5.2 有共享库/索引的项目可在 generation spec 中提交 `asset_backfills[]`，由下游项目驱动器调用本 skill 的规范和脚本直接完成确定项：

1. `create` 必须提供完整标准资产卡、资产类型与剧本证据；`supplement` 只允许追加出现集、别名或说明。缺字段、负向词污染或类型专属构图不合格时拒绝。
2. 写库前锁定项目；以当前 V{N} 为事实源生成 V{N+1}，旧库不得覆盖。多集同时提交的同名同类型同卡可合并复用；同名异类型、同名异体或卡正文冲突不得自动选版。
3. 重建有效可引用清单、角色音色表、图片文件名对照表和必要状态时间线；用 `sync_asset_index.py` 生成同版本索引。
4. 运行 `validate_assets.py --prev <V{N}> --index <V{N+1}索引>` 与 `audit_source_coverage.py --project <项目或scripts目录>`。任一 FAIL 时不切换下游配置、不写 applied receipt。
5. 全部通过后，下游一次提交新库、新索引、project.json、派生简报与 generation spec receipt。receipt 至少锁定目标名、类型、动作、库/索引路径及 SHA-256。
6. 改名、废弃、单状态首拆多状态和需要解释实体同一性的歧义继续走受控通道，不属于自动直回填。

此通道处理 A 新建和 B 补充确定项；季级回填台账保留给旧版 inline、C 改名、D 不入库和 E 待拍板，不应重复收割已经带 applied/existing receipt 的条目。

## 批量建库

长篇项目按 EP 顺序处理，每批以可完整消化为准，建议 10–15 集：

1. 分批前先读全量 `plot-map.md` / `progress.md` 的命名台账。
2. 首批产出 V1；后续批次每批走更新模式，输出 V+1。
3. 每批先读上一版「可引用 @资产清单」与所有「别名」行，新候选先查重。
4. 命中已有名或别名时追加出现集，不重复建卡。
5. 每批运行 `validate_assets.py --prev <上一版> --index <新索引>`。

不要并行写同一资产库文件。若使用多个工作单元做只读提取，最终归并、写盘和机检必须由一个实例串行完成。

## 终版收口

全部批次完成后执行：

1. 回填全部元信息块的出现集与别名。
2. 从当前全部 EP 重新提取场次头、出场人物、独立说话人和前景锁定指令；不得沿用早期 `progress.md` 的旧登记数量代替当前剧本。
3. 对每个重复人物标签执行精确资产名/别名闭合；具名固定前景或跨集说话人不得只落到“无具名面孔”群像。
4. 对每个重复场次头执行唯一物理空间映射；旧称、新称、机构更名和前后缀扩写并入别名，排除一处多卡和模糊包含匹配。
5. 全剧本重做一次群像排查；不能沿用首批零群像结论。
6. 对账可引用清单、音色表、特效表、状态时间线与图片文件名表。
7. 重新生成同版本索引。
8. 运行 `validate_assets.py` 与 `audit_source_coverage.py --project <项目目录>`；重复人物缺口、角色/群像映射冲突、高强度单集人物未决策、年龄变体漏状态、重复场景缺口、场景一对多映射和日夜证据不闭合必须清零。
9. 以最后一个稳定版为 `--prev` 运行全量机检；修复至 PASS 或仅剩已登记的一次性 inline warning。

库终版或阶段稳定版交给下游。中途升库后，用新库对已产出下游文件重跑引用机检。

## 交接建议状态闭环

项目存在 `visual-assets/handoff.md` 时，`## 全局实体索引` 表中 `建议@资产名` 或 `建议@集合` 的每个 `@资产名` 都进入强制闭环，且该闭环独立于 READY 导入和哈希校验：

1. 先运行 `audit_handoff_suggestions.py <handoff>` 提取唯一建议名清单；同一单元格中的多个状态逐项保留。
2. 对每个建议名先扫描 `visual-assets/episodes/EP-*.md` 的精确建议 `@` 并汇总该状态实际出现集，再回到对应当前 `scripts/EP-*.md` 核验状态事实；剧本信息不足时检索 `novel`，其余审美留白使用与状态语义一致的克制美术补足，并在说明中标注。状态卡出现集与时间线生效集使用同一精确集合，连续段压缩、离散段保留，不继承实体总出现集。
3. 同一实体的多个建议名构成一个状态族。每个建议名生成独立完整卡，族内基础锚点逐字相同，状态段只改变有证据或已授权补足的静态可见变量；角色音色逐字相同。
4. 多状态族使用建议状态卡，不另建基础总卡。每个建议名同步进入状态时间线、可引用清单和图片文件名对照表。
5. 完整建库、覆盖重建或升版完成后运行 `audit_handoff_suggestions.py <handoff> --library <资产库>`；`missing_count=0`、`state_episode_mismatch_count=0`、`timeline_episode_mismatch_count=0` 才完成交付。
